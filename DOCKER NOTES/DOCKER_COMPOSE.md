# Docker Compose

## 1. What is Docker Compose?

Docker Compose is a tool used to define and run multiple Docker containers using a single YAML configuration file.

Without Docker Compose, we have to run each container separately using `docker run`.

With Docker Compose, we can start all the required containers using a single command.

```bash
docker compose up -d
```

### Example

Our Todo App has two Docker images:

- `03asad/todo-client:v1` — React frontend
- `03asad/todo-server:v1` — Node.js/Express backend

Docker Compose allows us to start both containers together.

---

## 2. What is a Compose YAML File?

A Compose file defines the configuration of our application's containers.

The default filenames are:

- `compose.yaml`
- `compose.yml`
- `docker-compose.yaml`
- `docker-compose.yml`

We created `compose.yaml` in the root directory of our Todo App.

Project structure:

```text
todo-app/
├── client/
├── server/
│   └── .env
└── compose.yaml
```

---

## 3. Our Todo App `compose.yaml`

```yaml
services:
  todo-server:
    image: 03asad/todo-server:v1
    container_name: todo-backend
    ports:
      - "3000:3000"
    env_file:
      - ./server/.env
    restart: unless-stopped

  todo-client:
    image: 03asad/todo-client:v1
    container_name: todo-frontend
    ports:
      - "5173:80"
    depends_on:
      - todo-server
    restart: unless-stopped
```

This file defines two services: the backend and the frontend.

---

## 4. Understanding the YAML Properties

### `services`

```yaml
services:
```

Defines the containers/services required by our application.

In our project, we have two services:

- `todo-server`
- `todo-client`

### `image`

```yaml
image: 03asad/todo-server:v1
```

Specifies which Docker image should be used to create the container.

Our images are already available on Docker Hub, so we don't need to build them again on another machine.

Docker Compose pulls an image if it isn't available locally.

### `container_name`

```yaml
container_name: todo-backend
```

Assigns a specific name to the container instead of relying on the name generated by Docker Compose.

Our containers are named:

- `todo-backend`
- `todo-frontend`

### `ports`

```yaml
ports:
  - "3000:3000"
```

Port mapping follows this format:

```text
HOST_PORT:CONTAINER_PORT
```

For our backend:

```yaml
ports:
  - "3000:3000"
```

Port `3000` on our PC maps to port `3000` inside the backend container.

For our frontend:

```yaml
ports:
  - "5173:80"
```

Port `5173` on our PC maps to port `80` inside the frontend container.

We can access the application at:

- Frontend: http://localhost:5173
- Backend: http://localhost:3000

The container ports must match the ports on which the applications actually listen.

### `env_file`

```yaml
env_file:
  - ./server/.env
```

Loads environment variables from the specified file into the backend container.

Our backend needs its environment variables, including the MongoDB Atlas connection string.

The path is relative to the directory containing `compose.yaml`.

**Important:** Never commit database credentials or other secrets to a public GitHub repository.

### `depends_on`

```yaml
depends_on:
  - todo-server
```

Specifies that the backend service should be started before the frontend service.

It does not guarantee that the backend is fully ready to accept requests.

Also, this setting does not automatically configure the frontend's API URL.

### `restart`

```yaml
restart: unless-stopped
```

Defines the container's restart policy.

This property is optional.

Common restart policies:

| Policy | Behaviour |
|---|---|
| `no` | Default; no automatic restart |
| `always` | Automatically restarts the container when it stops, subject to Docker's restart behaviour |
| `unless-stopped` | Restarts automatically unless explicitly stopped |
| `on-failure` | Restarts when the container exits with an error |

For our Todo App, `unless-stopped` is useful because it allows the containers to restart after crashes or Docker daemon restarts unless we intentionally stopped them.

## 5. Docker Compose Networking

By default, Docker Compose creates a network for the application and connects its services to that network.

Therefore, we don't need to manually create a network for our frontend and backend.

### How containers communicate

Containers on the Compose network can communicate using service names.

For example, the backend service can be reached by other containers using:

```text
todo-server:3000
```

However, our React frontend code executes in the user's browser. The browser cannot automatically resolve Docker's internal service names.

For browser-based API requests, the frontend must use a backend URL reachable from the browser, such as:

```text
http://localhost:3000
```

This example works when the browser and published backend port are on the same PC.

For access from other PCs, configure a reachable server address and appropriate network access.

### What about our existing `todo-network`?

We previously created a custom Docker network named `todo-network`.

We don't need to reuse it because Compose creates its own network automatically.

If we want to reuse the existing network, we can configure it as an external network:

```yaml
networks:
  default:
    external: true
    name: todo-network
```

The external network must already exist.

## 6. Docker Volumes in Docker Compose

Volumes are used to persist data beyond the lifecycle of a container.

For example, when running MongoDB in a container, we generally use a volume to preserve database files.

### Example: MongoDB with a Named Volume

```yaml
services:
  mongodb:
    image: mongo
    volumes:
      - mongo_data:/data/db

volumes:
  mongo_data:
```

In this example:

- `mongo_data` is a named Docker volume.
- `/data/db` is the directory inside the MongoDB container where database files are stored.
- Docker manages the volume, allowing database data to persist even if the MongoDB container is removed and recreated.

### Do we need a volume in our Todo App?

No MongoDB Docker volume is needed for our current setup because our backend connects to MongoDB Atlas, which is a cloud database.

Our frontend and backend containers don't require a persistent data volume for the current application configuration.

### MongoDB and Backend with Both Network and Volume

If we run MongoDB as a Docker container instead of using MongoDB Atlas, we generally use a volume for database persistence and a network for communication between MongoDB and the backend.

```yaml
services:
  mongodb:
    image: mongo
    volumes:
      - mongo_data:/data/db
    networks:
      - todo-network

  backend:
    image: your-backend-image
    environment:
      MONGO_URL: mongodb://mongodb:27017/todo
    depends_on:
      - mongodb
    networks:
      - todo-network

volumes:
  mongo_data:

networks:
  todo-network:
```

**How it works:**

- `mongo_data:/data/db` persists MongoDB database files.
- `todo-network` connects the MongoDB and backend containers.
- `mongodb:27017` uses the MongoDB service name and its internal port.
- `depends_on` starts the MongoDB service before the backend, but doesn't guarantee MongoDB is ready to accept connections.

### Important Notes

- **Network:** Enables communication between containers.
- **Volume:** Persists data beyond a container's lifecycle.
- Docker Compose automatically creates a default network for its services, so explicitly defining a custom network is optional.
- A volume is not mandatory for every container, but persistent database storage is generally recommended.
- If MongoDB Atlas is used, a MongoDB container and its Docker volume are unnecessary.


## 7. Docker Compose Commands

### Validate the Compose configuration

```bash
docker compose config
```

Checks the Compose file and displays its resolved configuration.

### Start the application

```bash
docker compose up -d
```

Creates and starts the required containers in detached mode.

If images are missing locally, Compose pulls them from the configured registry.

### Build images and start services

```bash
docker compose up --build -d
```

Builds services that have a `build` configuration before starting them.

Our current Compose file uses `image`, not `build`, so this command isn't necessary for our current setup.

### Check running containers

```bash
docker compose ps
```

Displays the containers associated with the current Compose project.

### View logs

```bash
docker compose logs
```

Displays logs from the services.

### Follow logs continuously

```bash
docker compose logs -f
```

Streams logs as they are produced.

### View logs for one service

```bash
docker compose logs todo-server
```

Displays backend service logs.

```bash
docker compose logs todo-client
```

Displays frontend service logs.

### Stop and remove Compose containers

```bash
docker compose down
```

Stops and removes the containers and the default Compose network.

It does not normally delete named volumes unless `-v` is specified.

### Restart services

```bash
docker compose restart
```

Restarts the existing Compose containers.

### Stop services without removing containers

```bash
docker compose stop
```

Stops the containers while keeping them available for a later start.

### Start previously stopped services

```bash
docker compose start
```

Starts previously created, stopped containers.

## 8. Important Difference: `docker run` vs. Docker Compose

### Using `docker run`

We start containers individually:

```bash
docker run -d -p 3000:3000 \
  --env-file ./server/.env \
  --name todo-backend \
  03asad/todo-server:v1
```

We would then need another command to start the frontend.

### Using Docker Compose

We define both services in one file and start them together:

```bash
docker compose up -d
```

Compose also manages the default network and the application's service configuration.

## 9. What Happens When We Update an Image?

Our current Compose file uses versioned images:

```yaml
image: 03asad/todo-client:v1
image: 03asad/todo-server:v1
```

If we publish new images as `v2`, we must update the image tags in `compose.yaml`.

Then run:

```bash
docker compose pull
docker compose up -d
```

`docker compose pull` downloads the images specified in the Compose file.

`docker compose up -d` recreates containers when Compose detects that their image or configuration has changed.

A running container does not automatically update merely because a new image was pushed to Docker Hub.

---

## 10. Important Notes

1. Docker Compose is used to manage multiple related containers through one configuration file.
2. Compose automatically creates a default network unless configured otherwise.
3. Volumes are useful for persistent data, particularly database files.
4. `depends_on` controls service startup order but does not guarantee application readiness.
5. `restart` is optional and defines the restart policy.
6. The Compose file's image tags determine which images will be used.
7. `docker compose down` removes containers and the default project network, but normally preserves named volumes.
8. Environment files must exist at the specified paths.
9. Browser-based frontend requests must use an API URL accessible to the browser.
10. Docker Compose doesn't automatically build or publish new images unless the appropriate build configuration and commands or automation are used.
